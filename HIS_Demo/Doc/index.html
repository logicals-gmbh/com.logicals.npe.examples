01 / Overview

A compact packaging demonstrator

The application represents a carton entering a station, being sealed and leaving on a conveyor. A separate safety function controls the permit; the standard process logic handles timing, operating commands, a simulated jam and the production counter.

The demonstration story

Release the emergency stop, acknowledge safety, enable the line and start one carton. Show its progress, interrupt it or simulate a jam, then demonstrate deliberate recovery without an automatic process restart.

Timing and target selection matter.

The RevPi source specifies the runtime type HisLinuxA64. Short button presses may be missed between scans, especially with the 500 ms task. Hold a button long enough to be sampled, then release it. Timer transitions and heartbeat indications are quantised by the task cycle. The listed ports are engineering / NCF ports, not OPC UA endpoints.

Switching to a Windows or built-in configuration does not remove the I/O assignments in the program. A software-only test of this source revision needs suitable test inputs; it does not automatically restore the earlier simulation variant.

04 / Operator quick start

Run the demo in six steps

  1. Prepare the line

    Load the matching configuration and application, put the runtime in RUN and provide valid I/O. Release all three pushbuttons. For a normal cycle, keep CmdStop, CmdJam and CmdAckJam FALSE. Start with CmdFastCycle = FALSE.

  2. Release the emergency stop & reset safety

    The EStop input must become TRUE (released). Press and release Button 2. Check Safety.S_Permit = TRUE; S_DemoEnable mirrors this status. Reset acknowledges safety only; it does not start a carton.

  3. Enable the packaging process

    Press and release Button 1. Its rising edge toggles CmdEnable ON. Holding it down does not repeatedly toggle it. A Button 1 already held at program startup is ignored until released and pressed again.

  4. Wait for READY, then start one carton

    Check Line.Ready = TRUE and the ready lamp. Keep Button 3 released for at least one scan while READY, then press and release it. The application accepts a fresh start edge; enabling and starting together is insufficient.

  5. Follow the package

    Observe INFEED → SEALING → OUTFEED → COMPLETE. Conveyor and sealing lamps flash during their respective phases. Line.CartonsPacked increases by one at successful outfeed completion. After the completion display, the line returns to READY; press Button 3 again for another carton.

  6. Demonstrate interruption & recovery

    Button 1 toggles enable OFF. An emergency-stop demand removes the safety permit. After an emergency stop, release it and reset with Button 2, check enable and wait for READY, then issue a fresh Button 3 press. An interrupted carton sequence starts again at INFEED; it does not resume halfway through.

For a clear exhibition demonstration:

Show one normal carton, one fast carton, a simulated jam with acknowledgement, and finally an emergency-stop interruption followed by deliberate reset and a new start.

Important for HMI / OPC UA operation of this revision

CmdStart and CmdSafetyReset are overwritten from physical inputs every scan. Direct HMI writes to them cannot reliably operate this program. Likewise, Sim_EStopReleased, S_EStopA and S_EStopB are derived cyclically from EStop. Use the physical controls for these functions. CmdEnable is a latch and may be set through an authorised software write as well as toggled by Button 1.

The separate gateway must expose the matching build and allow the intended command writes. On RTS Micro Safe, software variable writes require the applicable RUN (Test) mode and gateway permissions; a working OPC UA connection alone does not grant write access. Do not use software writes as a substitute for physical safety inputs.

S_DemoEnable is a safety-permit status, not the operator enable command. Some source comments still refer to the original RTS MAX simulation; the assignments and configuration files documented here describe the current implementation.

These are timer presets. Actual elapsed time includes task and state-transition delays. The demo simulates process progress with timers, not carton-presence feedback.

Blocked · state 0

Missing permit or disabled process takes priority over the sequence. Active timing is interrupted and the start is disarmed. Restoring enable and permit returns the process to READY unless a jam remains latched.

Carton jam · state 90

A jam during an active phase latches Line.Fault. Turning enable off or losing safety permission does not clear the latch. Clear Jam and send a new AckJam edge with enable and permit present.

Decision priority: disabled / no permit → latched process fault → stop → sequence

CycleDone pulses for one scan when outfeed finishes. CartonsPacked is not cleared by a process stop or safety interruption and saturates at 4,294,967,295. There is no counter-reset command; normal cold initialisation resets the non-retained state.

07 / Safety path

PLCopen blocks provide the permit

FBD · SF_Equivalent

Channel equivalence

Checks S_EStopA and S_EStopB. Activate is TRUE; DiscrepancyTime = T#100ms. Its safe equivalent output feeds the emergency-stop block.

This discrepancy setting is labelled as a demo placeholder in the source; it is not a validated physical response-time specification.

FBD · SF_EmergencyStop

Reset & permit

Activate is TRUE. S_StartReset and S_AutoReset are FALSE. Reset receives CmdSafetyReset; S_EStopOut becomes S_Permit.

SafetyDemand, ResetRequest, EquivalentDiag and EStopDiag support diagnosis. Error ORs the two block error outputs.

Current wiring in the program

Both logical E-stop channels are copied from the same EStop global. They are not two independently acquired physical contacts in this program. S_Permit gates the demonstration process; it is not assigned to a physical safe output here. The standard packaging sequence and its indicator outputs are demonstration logic.

10 / Troubleshooting

When the expected transition does not happen

Safety permit stays FALSE

Check EStop = TRUE, both derived channels, a complete Button 2 press / release and Safety.ResetRequest. Inspect EquivalentDiag, EStopDiag and Safety.Error against the installed PLCopen block documentation. Writing S_DemoEnable does not supply a permit.

Enable changes unexpectedly or the first press is ignored

Button 1 toggles on a sampled rising edge. It must first be released after startup. Holding it does not toggle repeatedly. Avoid simultaneous HMI writes and physical button operation on the same latch.

The process is enabled but will not start

Check permit, Line.Ready, and that Stop, Jam and AckJam are FALSE. Release Button 3 while in READY for at least one scan, then press again. A held start or a start simultaneous with enabling is not accepted.

HMI start / safety reset has no effect

This source revision maps those commands from Button 3 / Button 2 every scan. Use the physical buttons. Confirm the HMI and gateway expose the current project build and command ownership before using software-only controls.

The jam returns after an interruption

The process fault is intentionally latched across disable and permit loss. Set Jam FALSE, restore enable and permit, pulse AckJam, release it, then wait for READY and send a fresh start.

The line does not restart after releasing the E-stop

Release alone is insufficient: reset safety with Button 2, confirm the permit, check enable, then perform a new Button 3 press after READY. Enable may still be latched ON, but no carton restarts automatically.

Inputs or lamp flashes look slow in the built-in PLC

The supplied local configuration runs every 500 ms. It can miss short button presses and coarsens timing. Confirm which configuration is actually loaded; the RevPi and Windows Micro Safe files specify different intervals.

The additional SAFE globals do not change

They are a customer demonstration dataset rather than live signals. Their names describe plausible process values, but this application does not update them.
